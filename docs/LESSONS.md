# Уроки проекта PC_block_soft

База разобранных дефектов этого проекта (правило 14 методики dev-methodology). Межпроектная база — `references/lessons.md` скилла; читать обе: при разведке вехи — целиком, дальше — быстрые сверки затронутых классов (по смыслу дефекта, не по совпадению экрана).

Формат урока:

```markdown
### PL-<N>. <короткое правило>
**Симптом:** что увидели (кто нашёл: приёмка / ревью / заказчик FB-N, веха).
**Суть:** универсальная причина без привязки к стеку.
**Детект:** каким тестом, сценарием или проверкой это ловится.
**Правило:** как проектировать, чтобы не повторилось.
```

Классы: A — согласованность представлений; B — подсветки и подсказки; C — вёрстка и данные; D — расчёты и периоды (учёт времени, сутки, расписание); E — техника приёмки и CI.
Перед новым уроком — поиск похожего по классу: обновить существующий, а не дублировать.

## Класс A. Согласованность представлений

### PL-5. Нарушение, которое может оказаться штатным завершением, пишется с задержкой, а не сразу
**Симптом:** FB-1 (заказчик, 0.2.2): в журнале родителя постоянно «попытка обойти защиту» при выключении, перезагрузке и выходе из учётки, иногда по две подряд.
**Суть:** процесс исчезает раньше, чем приходит событие «сеанс заканчивается»: система закрывает процессы первой. Решение «обход или штатно» принято по неполным данным.
**Детект:** юнит-тесты на поддельных часах: гибель, затем конец сеанса или остановка службы в пределах окна ожидания, записей ноль; сеанс жив после окна, запись ровно одна. Приёмка FB1 (тестовый «конец сеанса» стража).
**Правило:** реакция защиты (перезапуск) остаётся мгновенной, а запись о нарушении ставится в ожидание и снимается подтверждением штатного конца (выход, исчезновение сеанса, остановка службы). Процесс сам сообщает о штатном закрытии (`GuardClosing`), но это сообщение продлевает ожидание и не стирает запись: иначе его используют для обхода.

### PL-6. Знак числа в тексте журнала форматируется явно
**Симптом:** FB-2: «доп. время +-60 мин».
**Суть:** шаблон с зашитым «+» не учитывает отрицательные значения.
**Детект:** тест текста для отрицательного, нулевого и положительного значения, в том числе числа из базы (`float64`).
**Правило:** любой текст со знаком числа строится веткой по знаку; для минуса U+2212, как в окне родителя.

## Класс D. Расчёты и периоды

### PL-7. Служба не верит датчику там, где знает больше него
**Симптом:** FB-3: при смене пользователя детский сеанс отключён, страж в нём не может открыть рабочий стол ввода, считает сеанс незаблокированным, время идёт (при окне на весь экран без ограничения).
**Суть:** датчик внутри сеанса слеп к состоянию самого сеанса; ответ «не знаю» трактовался как «можно считать».
**Детект:** тесты: сеанс отключён или заблокирован при снимке стража «активен, окно на весь экран» секунда не засчитывается; сведений нет, решает снимок; взрослый сеанс не влияет. Приёмка S33.
**Правило:** состояние «на экране» и «заблокирован» знает служба (WTS и события сеанса) и перекрывает снимок стража; нет сведений, снимок стража решает. Любое «лучше засчитать» в учёте времени должно иметь тест на ситуацию, где датчик слеп.

### PL-8. Свежее событие сильнее опроса, пока опрос не мог его увидеть
**Симптом:** S33 в CI: событие «отключение» поставило «не на экране», но периодическая сверка списка сеансов через секунду вернула «на экране» (список ещё показывал «активен»).
**Суть:** состояние из события и из опроса идут с разной задержкой; опрос перебивает более свежую правду.
**Детект:** тест с устаревшим списком после события отключения: состояние держится.
**Правило:** после события состояние удерживается короткий срок (`offHold`, 5 с); дальше решает опрос. Признак, который снимается только событием (блокировка), дополнительно сбрасывается по независимому свежему признаку (снимок стража «активен» с вводом), чтобы потерянное событие не остановило учёт навсегда.

## Класс E. Техника приёмки и CI

### PL-1. Упавший шаг CI обязан сам рассказать, почему упал
**Симптом:** первая серия R4 (Фаза 0) красная, а журнал и артефакт с логом из песочницы агента скачать нельзя: причина неизвестна, починка вслепую.
**Суть:** диагностика, доступная только в месте, куда исполнитель не может попасть, равна отсутствию диагностики; канал «почему упало» должен работать в той среде, где идёт отладка.
**Детект:** проба: намеренно уронить шаг и проверить, что причина видна через `gh api .../check-runs/<job>/annotations`.
**Правило:** каждый шаг CI, который может упасть, пишет вывод в `$RUNNER_TEMP/ci.log`; в конце job — шаг `if: failure()` с `tools/annotate-errors.sh`; серия R4 публикует итог пометкой `::notice`.

### PL-2. Скрипт с кириллицей в выводе на Windows задаёт кодировку сам
**Симптом:** скан текстов интерфейса на Python проходит на Linux и, вероятно, падал в серии R4 на windows-latest (после фикса серия зелёная).
**Суть:** консоль Windows по умолчанию не UTF-8; печать кириллицы в Python без явной кодировки падает с UnicodeEncodeError.
**Детект:** запуск скрипта с `PYTHONIOENCODING=ascii` локально не падает.
**Правило:** Python-скрипты проекта вызывают `sys.stdout.reconfigure(encoding="utf-8")`; серия экспортирует `PYTHONIOENCODING=utf-8` (грабли методики: Windows / Git Bash).

### PL-3. Крупный временный буфер в долгоживущем процессе надо вернуть ОС явно
**Симптом:** приёмка S1 (веха M1) намерила у службы в простое ~70 МБ при пороге NFR-5 ≤ 50 МБ; страж и значок в норме. Пик давал рабочий буфер Argon2id 64 МБ (NFR-9) при хешировании пароля.
**Суть:** сборщик мусора со средой выполнения (здесь Go) отдаёт освобождённые страницы ОС лениво — рабочий набор долгоживущего процесса остаётся раздутым после разовой тяжёлой по памяти операции, даже когда объект уже мусор. Требование «ресурсы в простое ≤ X» проверяет рабочий набор, а не живую кучу.
**Детект:** замер рабочего набора процесса в простое через время после тяжёлой операции (приёмочный S1: после настройки/хеша ждать до 90 с, порог ≤ 50 МБ), а не сразу и не по размеру живой кучи.
**Правило:** после редкой операции, аллоцирующей крупный временный буфер (хеш пароля, разбор большого списка), принудительно вернуть память ОС (`debug.FreeOSMemory` в Go) — у операции не на горячем пути цена полной сборки приемлема; порог ресурса при этом не ослаблять.

### PL-4. Пакет субагента, описывающий «как уже устроено», сверять с кодом до работы
**Симптом:** в пакете писателю (раунд D-40) оркестратор утверждал, что реальный выход из учётной записи (logoff) в тестовом режиме подавлен. На деле подавления не было — приёмка просто не нажимала эту кнопку. Писатель сверил с кодом и сообщил расхождение, не сломав поведение.
**Суть:** раздел пакета «что уже готово, переиспользуй» — это утверждение оркестратора о чужом коде; если оно неверно, исполнитель либо строит на ложной опоре, либо тратит возврат на выяснение. Надёжная опора — только проверенный факт из кода, а не память оркестратора.
**Детект:** в пакете каждый механизм-опору сопровождать точным адресом (файл:функция), по которому исполнитель сверит факт первым делом; расхождение — эскалация, а не молчаливая адаптация.
**Правило:** перед выдачей пакета оркестратор проверяет grep'ом/чтением каждое «уже сделано, опирайся на это»; формулирует как «проверь X в <файл>», а не как данность. Новую инвариант-гарантию (подавление реального действия в тестовом режиме) вводит явной задачей, а не предполагает существующей.

### PL-9. Идентификатор от внешней системы в бою нулевой, а тесты передают настоящий
**Симптом:** ревью 0.2.3 (Critical): `OnSession(ev, 0, …)` в Windows-хосте, номер сеанса из события не читался. Всё, что привязано к номеру (снятие ожидания при выходе, признак блокировки), работало только в юнит-тестах.
**Суть:** тестовая обвязка подставляла значение, которого боевой код не получает; тесты зелёные, поведение в бою не работает.
**Детект:** на границе с внешней системой вынести разбор в маленькую тестируемую функцию (`sessionIDOf`) и тест на путь «не удалось прочитать»; ревью границы: откуда берётся каждый аргумент в боевом вызове.
**Правило:** внешний идентификатор читается и проверяется на границе; есть явный безопасный путь «неизвестно» (`SessionUnknown`: ничего не снимать вслепую, сверить весь список). Тесты не подставляют то, чего боевой код не получает.

### PL-10. Образ CI-раннера возвращает консоль после отключения сеанса
**Симптом:** S33: после `tsdiscon` через ~1 с сеанс снова на экране; сценарий, измерявший рост счётчика за 8 с, падал, хотя служба работала верно (журнал: отключение, WTS 4, снимок не учитывается).
**Суть:** сценарий проверял то, чего среда не даёт.
**Детект:** подробный журнал службы в диагностике сценария (`qwinsta`, строки про сеансы).
**Правило:** сценарии на состояние сеанса проверяют цепочку событий по журналу службы; полный эффект («время стоит, пока сеанс отключён») проверяется вручную на запасном ПК, строка в `docs/06_Приёмка.md`.

### PL-11. Диагностика и тестовые настройки включаются после настройки программы
**Симптом:** первый прогон S33 с подробными логами упал: `SetDiag` вызван до настройки ребёнка, служба ответила «Программа ещё не настроена».
**Суть:** порядок шагов в сценарии не соответствовал состоянию программы.
**Детект:** локально по порядку шагов; в CI падение на первом же обращении.
**Правило:** действия, которым нужна настроенная программа, идут после `Start-Child`/настройки.

### PL-12. Контроль, который поглощается предыдущим ожиданием, ничего не доказывает
**Симптом:** FB1: контрольное «принудительное завершение стража записывается» падало, потому что запись уже ждала 30 с после штатной гибели, а сценарий ждал 15 с; при исправленном ожидании одна запись покрывает обе гибели.
**Суть:** второе событие внутри окна ожидания не создаёт отдельного следствия.
**Детект:** проверять число записей и интервал, а не факт появления записи.
**Правило:** контроль либо выжидает истечения предыдущего окна, либо проверяет счётчик; помнить, что контроль «слабее» не значит «зелёный».
