## Правила работы с репозиторием (D-35, D-36)

1. **ТЗ правится заменой.** Изменение требования — сначала в `docs/01_ТЗ.md`: переписать раздел так, будто так было всегда; неверное удалить (и в других разделах); никаких приписок в конце, «было/стало», закрытых вопросов, истории. Версия ТЗ в шапке: уточнение 1.0 → 1.1, крупное 1.x → 2.0. Хронология — запись в `docs/HISTORY.md`. Новое решение заказчика — строка D-N в `docs/03_Решения_интервью.md`. Только потом код.
2. **Документы** (ТЗ, журналы, README, планы) — коммит прямо в main.
3. **Код** — в ветке `feature/<кратко>` или `fix/<кратко>`, Pull Request в main, исполнитель сам сливает (merge commit), когда CI зелёный. Заказчик ничего не нажимает в GitHub.
4. Коммиты — Conventional Commits, описание на русском в повелительном наклонении: `feat: добавить экран блокировки`. Типы: feat, fix, docs, test, refactor, build, ci, chore.
5. В конце каждой сессии — запись в начало `docs/HISTORY.md` (шаблон — там же, первая запись).
6. Новая версия для заказчика: `internal/version/version.go` и `wails.json` (productVersion) вместе (тест сверяет), раздел в `CHANGELOG.md`; сборка main публикует установщик в Releases.
7. Force-push, удаление данных, изменения вне репозитория, запуск блокировок на компьютере заказчика — только с его явного согласия.

## Среда облачной песочницы (грабли, пойманные в Фазе 0)

- Прокси модулей Go (`proxy.golang.org`) и «красивые» домены модулей (`golang.org/x`, `modernc.org`, `gopkg.in`…) из песочницы закрыты; модули с github.com качаются при `GOPROXY=direct`. Поэтому **локально собирается и тестируется только код на стандартной библиотеке**: `GOFLAGS=-mod=mod GOPROXY=off go test -race -count=1 ./internal/<пакет>/...`. Всё, что зависит от Wails, SQLite и Windows, проверяет CI.
- **go.sum обновляет CI сам**: после push рабочей ветки `ci.yml` делает `go mod tidy` и коммитит результат в ветку — затем `git pull`. Коммит бота новых проверок не запускает; сборка продолжает уже с ним.
- Go 1.27 в песочнице: если `go version` старее, поставить из релизов GitHub `actions/go-versions` (манифест `https://raw.githubusercontent.com/actions/go-versions/main/versions-manifest.json`) в `~/.local/go1.27` и добавить в PATH. Сайт go.dev закрыт.
- npm работает (`registry.npmjs.org`): `cd frontend && npm ci && npm test && npm run build` — локально.
- Браузеры Playwright в песочницу не скачиваются: снимки экранов — только в CI (`ci.yml`, job «Снимки экранов»).
- Удалённый адрес репозитория: `https://github.com/xgeorgeramirez-git/PC_block_soft.git`.
- GraphQL GitHub из песочницы закрыт: `gh pr create` и `gh pr merge` не работают. Pull Request: `gh api repos/xgeorgeramirez-git/PC_block_soft/pulls -f title=… -f head=<ветка> -f base=main -F body=@файл.md`; слияние: `gh api -X PUT repos/xgeorgeramirez-git/PC_block_soft/pulls/<N>/merge -f merge_method=merge`. `gh run list/view/watch` работают.

## Проверки CI без лишних запусков (PL-51, D-81)

6 ноября 2026 GitHub заблокировал аккаунт (обращение 4968101; восстановлен 10.11.2026). По словам заказчика (D-81), причина — не число запусков проверок: дневного ограничения на прогоны Windows нет. Правила ниже — ради скорости и чистоты истории, а не ради лимита:

1. Всё, что можно, проверять локально (фронт: `npm test`, `npm run build`; Go на стандартной библиотеке: `go test -race`; gofmt, скан текстов, `GOOS=windows go vet`). CI — подтверждение, а не место отладки.
2. Пушить пачкой: несколько готовых коммитов одним `git push`, а не каждый коммит отдельно. Помнить: push в ветку с открытым PR запускает `ci.yml` дважды (push и PR) и `windows.yml`, если менялся не только текст `*.md`, `docs/`, `plans/`.
3. Сценарии Windows — одним прогоном списком: `gh workflow run windows.yml --ref <ветка> -f scenario=accept -f only=S1,S4,…`, а не по прогону на сценарий.
4. Ограничения числа прогонов Windows в день нет (D-81): гонять столько, сколько нужно для дела, но не вместо локальной отладки.
5. Полный регресс и R4 — на закрытии вехи; после ревью-фиксов — затронутые сценарии (повторить полный регресс можно, если нужно).
6. Если `gh api user` или push отвечает «suspended» — остановиться и сообщить заказчику.

## CI и лестница прогонов (минуты Windows дороже вдвое)

| Уровень | Где | Когда |
|---|---|---|
| R0–R2 | `ci.yml` на ubuntu: фронт (типы, vitest, сборка), go.mod/go.sum, gofmt, скан текстов, `GOOS=windows go vet`/`go build` с тегами `desktop,production`, `go test -race` (кроме `internal/ui` и `main`), снимки Playwright → ветка `screenshots`, папка `screens/<ветка>/`; на PR — проверка актуальности `docs/CODEMAP.md` | каждый push и PR |
| R3 | `windows.yml` на windows-latest: `wails build -nsis`, сверка биндингов `frontend/wailsjs/go`, тесты Go на Windows, снимок настоящего окна (`tools/win-window-screenshot.ps1`) → ветка `screenshots`, тихая установка и удаление, артефакты установщика; на main — выпуск в Releases | PR в main, push в main, вручную |
| R4 | `full-series.yml` на windows-latest: `tools/test-series.sh` (статика, гонки, покрытие по `tools/coverage-thresholds.txt`, фаззинг всех `Fuzz*` по 60 с, vitest) | вручную (`gh workflow run full-series.yml --ref <ветка>`) на закрытии вехи и после ревью-фиксов |

Чтение результатов: журналы и артефакты Actions из песочницы **не скачиваются** (домены хранилища закрыты). Поэтому упавшие шаги публикуют строки ошибок пометками сборки (`tools/annotate-errors.sh`), серия R4 — ещё и итог пометкой `::notice`. Смотреть: `gh run list --branch <ветка>`; шаги — `gh run view <id> --json jobs --jq '.jobs[] | .databaseId as $j | .steps[] | "\($j) \(.name): \(.conclusion)"'`; ошибки — `gh api repos/xgeorgeramirez-git/PC_block_soft/check-runs/<job-id>/annotations --jq '.[] | .title + "\n" + .message'`. Новый шаг CI, который может упасть, пишет вывод в `$RUNNER_TEMP/ci.log` (`exec > >(tee -a "$RUNNER_TEMP/ci.log") 2>&1`) — в конце job есть шаг пометок при сбое; снимки: `git fetch origin +screenshots:refs/remotes/origin/screenshots && git show origin/screenshots:screens/<ветка-через-дефис>/<файл>.png > <scratchpad>/<файл>.png`. Снимки разбирает агент `visual-reviewer` (главный агент картинки не читает).

## Структура

- `main.go` — запуск окна; встраивает `frontend/dist`.
- `internal/ui/` — связка окна Wails (методы App для интерфейса). Логики правил здесь нет.
- `internal/version/` — номер версии.
- Будущее (M1): `internal/core/` — ядро правил и учёта, **только стандартная библиотека**, порты (часы, датчики сеанса, процессы, правила браузера); `internal/storage/` — SQLite и миграции `internal/storage/migrations/NNN_имя.sql`; `internal/ipc/` — канал связи; `internal/service/`, `internal/guard/` — служба и страж сеанса (`*_windows.go`).
- `frontend/` — React + TypeScript + Vite; к программе — только через `frontend/src/api.ts`; биндинги `frontend/wailsjs/go/` коммитятся (CI сверяет с генерацией Wails).
- `build/appicon.png` — значок; остальные файлы `build/windows/` Wails генерирует при сборке (свои шаблоны NSIS — B-1).
- `tools/` — скан текстов, кодовая карта, серия R4, снимок окна, загрузка снимков.

## Ключевые правила для M1

1. Сначала проба неубиваемого экрана блокировки (ТЗ 3.2): страж от имени системы в сеансе ребёнка. Не вышло — запасной путь из ТЗ 3.2, решение оформить Ruling.
2. Ядро учёта и правил — без Wails и Windows, на портах; эталоны G1, G2, G3, G9, G10 → `testdata/golden/*.json` и тесты на поддельных часах.
3. Аварийный выход в каждой версии (NFR-10): S3, S7, S25, S26 — в регрессе каждой вехи.
4. Блокировки испытываются только в CI в тестовом режиме (детская учётка — тестовая учётка раннера, временная папка данных).
5. Тексты: ребёнку на «ты», родителю на «вы», без длинных тире (скан в CI), без технических ошибок (слой человеческих сообщений).
6. Go nil-слайс уходит во фронт как `null`: массивы в ответах инициализировать `[]T{}`.

## Грабли стека (из методики, применимы здесь)

- NSIS: скрипт `.nsi` — UTF-8 с BOM, иначе кириллица бьётся; комментарий, оканчивающийся на `\`, съедает следующую строку; деинсталлятор завершается раньше удаления — ждать.
- `go test -race` на Windows требует gcc (в R4 ставится mingw, если его нет); отсутствие race-прогона — не зелёная серия.
- После смены методов App — биндинги перегенерирует `wails build`; CI падает, если закоммиченные устарели.
- Тесты с датами: данные и ожидание из одной переменной; даты у границы суток — константами.
- Полный список — `references/gotchas.md` скилла dev-methodology.
