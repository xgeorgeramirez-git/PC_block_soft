# Веха M1 «Лимит времени с аварийным выходом» — Implementation Plan

> **Оркестратору вехи:** исполнение по Фазе 3 dev-methodology конвейером «два слота»; реестр — `plans/M1-agents.md`; скиллы — только «Skills to load» из этой шапки. Шаги с чекбоксами `- [ ]`.

**Goal:** первая рабочая версия 0.1.0 — у каждого ребёнка свой общий лимит по дням недели, значок с остатком, предупреждения 15/5/1, экран блокировки по исчерпании времени, снятие родительским паролем, сброс пароля и удаление из учётки администратора; ставится на запасной ПК.

**Architecture:** чистое ядро `internal/core` (только стандартная библиотека, порты: часы, датчики сеанса, управление процессами, журнал) считает активные секунды и решает «блокировать/нет»; `internal/storage` (SQLite, WAL) хранит детей, лимиты, состояние дня, события, пароль, настройки; `internal/auth` (Argon2id) — пароль; `internal/ipc` (именованный канал Windows) соединяет службу с окнами и стражем; `internal/service` (служба Windows) держит ядро и хранилище, запускает страж и значок в сеансах; `internal/guard` (страж, только Windows) — датчики, предупреждения, экран блокировки, запрет Диспетчера задач, самовосстановление; `internal/systray` — значок; `internal/ui` (Wails) — окно родителя и «Моя статистика» ребёнка; `internal/guidance` — каталог Помощника (данные + валидатор). Ядро и каталог тестируются локально; всё с Windows/SQLite/Wails — в CI.

**Tech Stack:** Go 1.27 + Wails v2.17 (WebView2) + React/TS/Vite + SQLite (`modernc.org/sqlite`, без CGO в прод-сборке); служба — `golang.org/x/sys/windows/svc`; окна стража — Win32 из Go; значок — systray на чистом Go; пароль — Argon2id (`golang.org/x/crypto/argon2`); установщик — NSIS. Тесты: `go test -race`, фаззинг, vitest, Playwright.

**Spec:** `docs/01_ТЗ.md` — разделы 1–5, 7, 8.0–8.2.3, 8.3.1–8.3.3, 8.3.8, 8.4, 9 (M1), 10, 11 (S1…S7, S25…S28); эталоны `docs/04_Эталоны_учёта.md` (G1, G2, G3, G9, G10). Решения D-1…D-38 — `docs/03_Решения_интервью.md` (read-only).

**Skills to load:** dev-methodology, git-guru, uiux-design, usability-heuristics, in-app-guidance (гейт-вопрос = «да», D-37); web-design-guidelines — только на ревью диффа интерфейса (Фаза 6).

## Решения Фазы 2 (Ruling: решение — почему — цена ошибки)

Сверка черновика плана с репозиторием (HEAD `f56bf72`) и с CI-воркфлоу дала решения ниже. Задачи плана написаны уже с их учётом.

1. **Гейт-вопрос Помощника.** Заказчик подтвердил 18.10.2026 в чате оркестратора вехи: «Да, как решено (D-37)». FR-34 (каркас и покрытие функций M1) и S28 — в объёме M1. — Ответ заказчика. — Цены нет.
2. **Одна программа с режимами вместо нескольких exe.** `PCBlock.exe` (сборка Wails) работает в режиме по ключу запуска: без ключа — окно (мастер, если программа не настроена, иначе вход родителя); `--service` (так служба запускается диспетчером служб), `--install-service`, `--remove-service`, `--guard`, `--tray`, `--parent`, `--mystats`, `--firstrun`, `--wizard`, `--reset-password`, `--uninstall-gate`, `--test-setup`, `--test-ipc`. Разбор ключей — пакет `internal/launch` (стандартная библиотека, тесты локально); `main.go` только передаёт управление. — В установщик кладётся один файл, шаблоны NSIS проще, нет отдельных сборок `cmd/*`. — Служба и страж несут код окон Wails: память замеряется в S1 (служба ≤ 50 МБ, страж ≤ 40 МБ, значок ≤ 40 МБ), полностью — ST5 в M7.
3. **Win32 напрямую через `golang.org/x/sys/windows`** (ленивые процедуры user32, gdi32, shell32, wtsapi32, advapi32, netapi32), без windigo и без библиотеки systray. — Значку нужна картинка с цифрами остатка и своя мини-панель по щелчку, стражу — тот же слой окон; меньше зависимостей с незнакомым API. Отличие от ТЗ 3.1 («библиотека systray на чистом Go») записывается в README «Отклонения от ТЗ». — Свой код значка около 300 строк; ловят снимки S1 и тесты картинки значка.
4. **Тестовый режим (ТЗ 10.8).** Ключ реестра `HKLM\SOFTWARE\PCBlock\TestMode` (писать может только администратор; нет ключа — обычный режим) со значениями `DataDir` (временная папка данных), `ClockSpeed` (ускорение часов, целое ≥ 1, по умолчанию 1), `ClockStart` (момент часов ядра в начале теста, например пн 19.10.2026 15:00 — чтобы день недели и полночь не зависели от времени запуска CI), `ClockRealStart` (реальный момент начала; пишется при включении режима, чтобы после перезапуска службы время ядра продолжалось, а не шло назад), `TestChildSID` (учётка раннера: только для неё сняты запрет A2 и правило R1 «администратор не ограничивается», ТЗ 10.8). Служба читает ключ при старте и пишет в журнал работы, что включён тестовый режим. Ускорение — через порт `Clock` ядра (`ScaledClock`), и служба в тестовом режиме тикает раз в секунду ЧАСОВ ЯДРА (реальный период 1 с / `ClockSpeed`), поэтому каждый тик — одна секунда учёта и правило разрыва (Ruling 13) работает как в обычном режиме. Ускоряются только учёт и время дня; по реальным часам идут: родительская сессия 10 мин, пауза 60 с после 5 неверных паролей, автозакрытие плашки 15 с, «Отменить» 10 с, сроки реакции NFR-6. Датчик бездействия в тестовом режиме умножает «время с последнего ввода» на `ClockSpeed`. Команда тестового режима `TestClock` ставит часы ядра на паузу и продолжает их (снимок плашки «Осталась 1 минута» при ускорении иначе не поймать). — S2, S6, S27 в реальном времени стоят около 100 минут Windows на один прогон. — Дефект, который проявляется только при реальном темпе, ловят эталоны на поддельных часах (G1, G2, G10) и ручная проверка на запасном ПК.
5. **Команды стража в тестах.** Окно стража от имени системы нельзя автоматизировать снаружи даже из процесса администратора (UIPI): это и есть защита от ребёнка. Поэтому в тестовом режиме служба принимает команду `TestGuard` (нажать кнопку, ввести текст в поле, послать себе WM_CLOSE / Alt+F4 / Esc), а страж выполняет её через настоящие сообщения своих элементов (BM_CLICK, WM_SETTEXT, PostMessage самому себе). Вне тестового режима служба такие команды отклоняет (на это есть тест). — Иначе S3 и S4 в CI не автоматизируются. — Путь «настоящее нажатие клавиш» проверяется только вручную на запасном ПК (строка в `docs/06_Приёмка.md`).
6. **Приёмка в CI** — задача T16: S-сценарии на windows-latest в тестовом режиме. То, что в CI не воспроизводится (второй интерактивный сеанс, настоящее выключение питания, окно UAC), помечается в `docs/06_Приёмка.md` как «вручную, запасной ПК» с указанием, какая часть сценария доказана в CI.
7. **Пороги покрытия.** Файла `tools/coverage-thresholds.txt` в репозитории нет, а шаблон `coverage*.txt` в `.gitignore` его скрывает; серия без файла молча пропускает проверку покрытия. Задача T2 создаёт файл (`internal/core 90`), добавляет в `.gitignore` исключение `!tools/coverage-thresholds.txt`; T7 и T8 дописывают `internal/storage 75`, `internal/ipc 80`. «Логика интерфейса ≥ 70 %» (ТЗ 10.4) — покрытие vitest для `frontend/src/lib/**` и `frontend/src/guidance/**` (пакет `@vitest/coverage-v8`, пороги в `vite.config.ts`, прогон с `--coverage` в серии R4) — задача T12.
8. **Линтер импортов (NFR-1)** — `tools/check_imports.sh` в R0 (`ci.yml` и серия R4): пакеты `pcblock/...` не импортируют `net`, `net/http`, `net/rpc`, `net/smtp`, `crypto/tls`. Канал связи — именованный канал через `x/sys/windows`, не пакет `net`. — Задача T2.
9. **Проба T1 — в отдельной ветке и отдельном рабочем дереве** `spike/m1-lock` (`git worktree`, свой воркфлоу `spike.yml` на push в `spike/**`), параллельно с ядром T2–T5 в основном дереве на ветке `feature/m1-time-limit`. Файлы не пересекаются, миграций и зависимостей между задачами нет (раздел методики «Параллельные линии»: два писателя только в разных деревьях, субагентов одновременно не больше двух). После Ruling пробы переиспользуемый код (`internal/winsession`, окно блокировки) вливается в `feature/m1-time-limit`, точка входа пробы `cmd/lockspike` и `spike.yml` удаляются. — Проба ждёт CI на Windows (минуты), ядро пишется и проверяется локально. — Пересечение файлов дало бы конфликт слияния: списки Files у T1 и T2–T5 не пересекаются.
10. **Предупреждение при позднем входе (R9):** «если до события меньше порога уже в момент входа, показывается ближайший меньший порог» читается буквально: прошедшие пороги не показываются, ближайший меньший срабатывает в свой момент (вход при остатке 3 мин → только предупреждение за 1 мин). ТЗ R9 переписан так однозначно (ТЗ 1.2). — Буквальное прочтение ТЗ. — Если заказчик ждал плашку сразу при входе, это правка в фидбек-раунде; остаток при входе и так виден в значке янтарным.
11. **«Готово» для M1 включает S28** (ТЗ, раздел 9, строка M1; гейт «да»), хотя в промте вехи перечислены S1…S7 и S25…S27.
12. **Сеансные процессы.** Значок — от имени пользователя в каждом интерактивном сеансе; страж — от имени системы только в сеансах детей (если проба T1 путь не подтвердит — запасной путь ТЗ 3.2); окна родителя, «Моя статистика» и первый вход запускает значок от имени пользователя сеанса. Все данные окна получают только через канал связи: база доступна лишь службе (ТЗ 3.4).
13. **Пересчёт времени тиками.** Служба вызывает ядро раз в секунду часов ядра (в тестовом режиме чаще, Ruling 4); ядро засчитывает за тик не больше секунды и ничего не засчитывает за разрыв больше 5 с по часам ядра (сон, гибернация, остановленная служба). — Иначе после выхода из сна ребёнку списалось бы всё время сна. — Небольшая недосчитанность при перегрузке машины укладывается в NFR-7 (≤ 1 мин за 8 ч).
14. **Мост окна — три метода с простыми типами.** `App.Call(command string, payload string) (string, error)` (JSON запроса и ответа канала связи как есть), `App.Mode() string`, `App.Version() string`. Типы запросов и ответов — в `internal/ipc` (Go) и `frontend/src/api.ts` (TS). — Биндинги Wails в песочнице не генерируются (модули закрыты), а `windows.yml` сверяет закоммиченные биндинги с генерацией; при простых типах Wails не создаёт `models.ts`, а `App.d.ts`/`App.js` пишутся вручную точно по образцу существующих (методы по алфавиту, аргументы `arg1`, `arg2`). — Рассинхрон типов Go и TS ловит контракт-тест: Go-тест `internal/ipc` пишет примеры ответов каждой команды в `internal/ipc/testdata/contract.json` (с флагом `-update`, файл коммитится, без флага тест сверяет), vitest читает тот же файл и проверяет, что `api.ts` их разбирает.

### Решения по ревью плана (m1-plan-review-2, 18.10.2026)

15. **Аварийный выход без службы (NFR-10, R18, D-28).** Пароль на экране блокировки проверяет служба, поэтому страж без связи со службой дольше 10 с (реальных) снимает экран блокировки и плашки и ничего не ограничивает; событие «страж без связи» пишется после восстановления связи. Остановка службы завершает стражей и значки во всех сеансах. В сеансе ровно один страж и один значок (мьютексы `Global\PCBlockGuard-<сеанс>`, `Global\PCBlockTray-<сеанс>`); служба при старте завершает оставшиеся от прошлого запуска процессы стража и значка и запускает новые. — Иначе упавшая или удалённая служба оставила бы экран, на котором пароль не работает. — Ребёнок не может остановить службу (она от имени системы), поэтому окно «без связи» не даёт ему обхода; проверка — `logic_test.go` (нет связи 10 с → экран снят) и шаг S27 «служба остановлена при показанном экране → экран снят ≤ 10 с, служба поднята → экран вернулся».
16. **R1 — в T9.** Служба проверяет, не стала ли детская учётка администратором (`NetUserGetLocalGroups` с `LG_INCLUDE_INDIRECT`), при входе в сеанс и раз в 60 с: стала → учёт и ограничения не действуют, событие в журнал, статус «Администратор: ограничения не действуют». Для `TestChildSID` в тестовом режиме проверка R1 и запрет A2 сняты (ТЗ 10.8 уточнён заменой текста, ТЗ 1.2). — Без исполнителя R1 не был бы сделан; без исключения тестовая учётка-администратор раннера не ограничивалась бы и S2–S6 упали бы.
17. **Безопасность канала (NFR-9).** Дескриптор канала `D:P(A;;GA;;;SY)(A;;GA;;;BA)(A;;0x12019b;;;IU)` (у интерактивных пользователей нет права создать свой экземпляр канала), `FILE_FLAG_FIRST_PIPE_INSTANCE`; ввод-вывод с перекрытием и `CancelIoEx` при остановке службы (блокирующий `ConnectNamedPipe` вешает остановку); личность клиента — `ImpersonateNamedPipeClient` + токен потока (SID, повышение, членство в Администраторах), PID — `GetNamedPipeClientProcessId` (сеанс, привязка родительской сессии); клиент до отправки любых данных (тем более пароля) проверяет, что сервер канала работает от имени системы (`GetNamedPipeServerProcessId` → владелец S-1-5-18). Снимки датчиков служба принимает только от системного стража того же сеанса. — Иначе процесс ребёнка мог бы занять имя канала, пока служба перезапускается, и получить пароль родителя из окна.
18. **Блокировка за обход хранится в базе.** ТЗ 4: в `children` поле `bypass_detail TEXT` (NULL — блокировки нет; иначе — что произошло), ТЗ уточнён заменой текста. Блокировка переживает перезапуск службы, повторный вход и смену суток; снимает только родитель паролем. — Иначе выход из учётки снимал бы блокировку за обход.
19. **Окна программы запускает служба.** Значок и страж просят службу открыть окно (`OpenWindow{kind}`), служба запускает `PCBlock.exe --parent` / `--mystats` / `--firstrun` в сеансе от имени пользователя (`LaunchAsUser`) и следит за процессом (FR-27, R17в для окон: процесс завершён не через интерфейс → окно открывается снова ≤ 3 с и событие обхода; штатное закрытие окна сообщает службе код 0). «Открыть настройки» с экрана блокировки: после верного пароля страж просит окно родителя с передачей родительской сессии; пока сессия родителя открыта, страж прячет экран блокировки; конец сессии (10 мин бездействия или закрытие окна) — экран возвращается, если ограничение ещё действует. — Окно Wails нельзя открыть из процесса от имени системы, а таймер «поверх всех» стража перекрывал бы окно родителя.
20. **Политика Диспетчера задач (FR-29).** `DisableTaskMgr=1` в `HKU\<SID ребёнка>\Software\Microsoft\Windows\CurrentVersion\Policies\System` пишется при входе ребёнка (`WTS_SESSION_LOGON`, раздел загружен) и при отметке учётки детской: если пользователь не вошёл, раздел профиля подгружается `RegLoadKey` (профиля ещё нет — запись при первом входе); снимается так же при удалении программы и при снятии отметки. Проверки: S1 (значение есть у ребёнка), S26 (значения нет после удаления). — При старте службы разделы детей обычно не загружены.
21. **Установщик и удаление.** Если программа ещё не настроена (пароль не задан), удаление пароль не спрашивает (ТЗ FR-4 уточнён заменой текста) — иначе текущий шаг `windows.yml` «Тихая установка и удаление» упадёт. Установка поверх старой версии сначала останавливает службу (ожидание остановки), завершает стражей и значки, затем копирует файлы; `--install-service` выдерживает повторный запуск. Удаление снимает ключ `SafeBoot`.
22. **Биндинги в рабочих ветках.** `windows.yml` при ручном запуске на ветке, отличной от main, коммитит сгенерированные биндинги в ветку (как `go mod tidy` в `ci.yml`) и сообщает об этом пометкой `::notice`; на Pull Request — как сейчас, расхождение роняет сборку. Запуск без ключа доходит до `wails.Run`, не обращаясь к каналу связи: генератор биндингов запускает сам бинарник. Методы моста и биндинги меняются в одной задаче (T9).
23. **Вывод служебных ключей.** Программа собрана как оконная (`-H windowsgui`), стандартного вывода у неё нет, поэтому `--test-ipc`, `--test-setup` и прочие служебные ключи пишут результат в файл `--out <путь>` (JSON) и код выхода; PowerShell вызывает их через `Start-Process -Wait`. Запуск от имени `pcbtest` — `Start-Process -Credential`; если вторичный вход на раннере недоступен — ключ `--test-runas` (`CreateProcessWithLogonW`, только в тестовом режиме).
24. **Экран блокировки M1.** Кнопки «Пароль родителя» (главная) и «Выйти из учётной записи»; «Попросить ещё» и «Взять из копилки» по ТЗ FR-6 относятся к M2 и в M1 не показываются (а не показываются недоступными: им нечего объяснять до M2). Выход из учётки — по просьбе стража служба вызывает `WTSLogoffSession` (из процесса системы `ExitWindowsEx` пользователя не выводит). Перехват клавиш глушит также Ctrl+Shift+Esc и Ctrl+Esc; рабочий стол (`Progman`, `WorkerW`) датчик не считает полноэкранным окном.
25. **Испорченная база (NFR-8, R18).** Служба не смогла открыть базу или проверка целостности не прошла → копия файла `pcblock.db.broken-<дата-время>`, ограничения не применяются, событие в журнал работы, родитель видит предупреждение при следующем входе; тест в T7 (испорченный файл) и T9 (служба в безопасном режиме).

## Global Constraints

Дословно из ТЗ и CLAUDE.md:

- **Форматы (ТЗ 4):** длительности в базе — целые секунды (лимиты — целые минуты); дата дня — строка `YYYY-MM-DD` по местному времени; моменты — UTC в миллисекундах + смещение пояса на момент события; текст — UTF-8. В интерфейсе: «1 ч 05 мин», «40 мин», «пн, 19 октября», «21:00».
- **Ядро на портах (ТЗ 3.3):** правила и учёт — без обращений к Windows; время, датчики сеанса, управление процессами, запись правил браузера — через интерфейсы. Ядро — только стандартная библиотека Go.
- **Эталоны — истина (правило 2):** расхождение расчёта с G1…G12 = ошибка кода. В M1: G1, G2, G3, G9, G10 → `testdata/golden/G*.json`, прогон на поддельных часах.
- **Никакой сети (NFR-1, NFR-2):** ноль сетевых соединений от любой части программы; без аккаунтов, рекламы, телеметрии, автообновлений. Линтер импортов в CI.
- **Никакой слежки (R23):** не делаются и не хранятся скриншоты, переписка, нажатия клавиш, адреса страниц, заголовки окон. Хранятся только путь и название программы, домен сайта, длительности, события журнала.
- **Аварийный выход (NFR-10, R18):** экран блокировки всегда принимает родительский пароль; учётки родителя и администраторов никогда не блокируются; при невозможности читать правила ограничения не применяются, ошибка — в журнал. S3, S7, S25, S26 — в регрессе каждой вехи.
- **Детская учётка — только обычная (A2, R1, D-38):** учётку администратора отметить детской нельзя; в CI в тестовом режиме запрет снят только для учётки раннера (ТЗ 10.8).
- **Тексты (NFR-11, ТЗ 8.0–8.1):** русские, ребёнку на «ты», родителю на «вы»; без длинных тире (скан CI); без технических текстов ошибок (слой человеческих сообщений); стиль сдержанный, без «AI-вида» (D-30). Палитра — ТЗ 8.0 п.9; цвет — только носитель статуса.
- **Пороги покрытия (ТЗ 10.4):** ядро `internal/core` ≥ 90 %; `internal/storage` ≥ 75 %; `internal/ipc` ≥ 80 %; логика интерфейса ≥ 70 %.
- **Go nil-слайс → `null` во фронт:** массивы в ответах инициализировать `[]T{}`, на фронте `?? []` (CLAUDE.md, урок Go/SQLite).
- **Коммиты:** Conventional Commits, описание на русском в повелительном наклонении. Код — ветка `feature/m1-time-limit` → PR → зелёный CI → merge в main самим исполнителем. Документы — прямо в main.
- **Лестница R0–R4:** тяжёлые прогоны строго по лестнице; `full-series.yml` (R4) — ровно на закрытии вехи и после ревью-фиксов. Блокировки — только в CI (D-29), на компьютере заказчика не запускать.
