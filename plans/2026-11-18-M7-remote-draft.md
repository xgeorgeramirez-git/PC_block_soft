# Черновик плана вехи M7 «Связь с телефоном» (версия 0.8.0)

Статус: **черновик планировщика** (18.11.2026). Веха-чат сверяет его с репозиторием, закрывает открытые вопросы с заказчиком и пишет полный план `plans/YYYY-MM-DD-M7.md` по методике (ревью плана свежим агентом).

**Goal:** родитель с Android-телефона видит остаток времени детей и добавляет или убавляет доп. время; компьютер связан с телефоном через сервер связи на VPS родителя.

**ТЗ 2.0:** FR-40, NFR-1 (связь), NFR-16, S55, S56; решения D-88, D-89, D-90; веха M7 (бывшая M7 «Финал 1.0» теперь M8).

## Архитектура (предложение)

```
Телефон (Android-приложение) ──HTTPS──► VPS: обратный прокси (уже есть у n8n) ──► контейнер pcblock-relay (127.0.0.1:порт)
                                                                                       ▲
Компьютер: служба PCBlock, пакет internal/remote ──── исходящее HTTPS (длинный опрос) ─┘
```

1. **Сервер связи `pcblock-relay`** — Go, только стандартная библиотека, один бинарник в маленьком образе (distroless/scratch), SQLite не нужен: JSON-файл или `bbolt` не тянуть — хватит файла в томе. Свой `docker compose` проект в `/opt/pcblock-relay`, порт только `127.0.0.1:<порт>`, HTTPS и домен — через уже работающий у n8n обратный прокси (какой — узнать по диагностике ниже). n8n, его compose и сеть **не трогать**.
   - Хранит: компьютеры (id, хэш ключа компьютера), привязки телефонов (id, открытый ключ Ed25519, имя), очередь команд в памяти (не копится: команда живёт ≤ 30 с), последний отчёт компьютера (по каждому ребёнку: проведено сегодня и остаток; время отчёта — по нему «На связи»).
   - API (черновик): `POST /v1/pc/register` (компьютер, ключ), `POST /v1/pc/pair-code` (код 6 цифр на 10 мин), `GET /v1/pc/poll` (длинный опрос ≤ 25 с: команды), `POST /v1/pc/report` (остатки, ответы на команды); `POST /v1/phone/pair` (код + открытый ключ телефона), `GET /v1/phone/status`, `POST /v1/phone/command` (подписанная команда), `DELETE /v1/phone/{id}`.
   - Ограничение частоты на пары по коду (5 попыток — блок на 10 мин), размер тела ≤ 16 КБ, журнал без токенов.
2. **Служба: пакет `internal/remote`** — единственный пакет с сетью (линтер импортов NFR-1: разрешить `net/http` только ему). Порт службы `RemoteLink` (тесты на подделке). Выключено по умолчанию; настройки в `settings`: адрес сервера, ключ компьютера, список телефонов (id, открытый ключ, имя, когда привязан).
   - Цикл: длинный опрос → команда → проверка подписи телефона (Ed25519, стандартная библиотека), номера и срока (защита от повтора: номер команды растёт, срок ≤ 60 с) → существующая логика доп. времени (`AddExtra`/`ReduceExtra`, R10, те же пределы и журнал с пометкой «с телефона») → отчёт с новым остатком.
   - Обрыв — повтор с паузой 1…30 с (экспонента с разбросом), ≤ 60 с восстановление (NFR-16). Сбой связи не трогает учёт и блокировки.
   - Привязка без доверия к серверу: код из окна родителя участвует в HMAC открытого ключа телефона — сервер не может подменить ключ (PL-класс «посредник»).
3. **Окно родителя:** «Настройки» → блок «Телефон»: выключатель «Связь с телефоном», поле «Адрес сервера», кнопка «Подключить телефон» (код 6 цифр крупно, срок), список привязанных телефонов с «Отвязать», строка «На связи / Нет связи с HH:MM». Новые команды ipc: `GetRemote`, `SetRemote`, `RemotePairCode`, `RemoteUnpair`.
4. **Android-приложение** `android/` — Kotlin + Jetpack Compose, minSdk 26. Экраны (D-91): «Подключение» (адрес, код); главный — компьютер «На связи» / «Не на связи с HH:MM», по каждому ребёнку «Сегодня за компьютером» и «Осталось», «+15», «−15», своё число. Отчёт компьютера на сервер — раз в минуту и сразу после команды. Ключ Ed25519 в Android Keystore (или Tink, если Keystore не умеет Ed25519 на minSdk 26 — решить в плане). Сборка APK в CI (`android.yml`, ubuntu, Gradle), подпись ключом из секретов GitHub, APK — в Releases рядом с установщиком.
5. **Приёмка:** S55, S56 на windows-latest — сервер связи запускается на раннере (тот же бинарник), «телефон» — тестовый Go-клиент `tools/remote-phone` с тем же протоколом и подписью. Приложение Android: юнит-тесты + сборка в CI; живую проверку на телефоне делает заказчик.

## Диагностика VPS (только чтение, ничего не меняет) — отправить заказчику в начале чата

```bash
uname -a; lsb_release -ds
docker --version; docker compose version
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}'
docker compose ls
sudo ss -tlnp | grep -E ':(80|443|5678)\b'
which nginx caddy traefik 2>/dev/null; ls /etc/nginx/sites-enabled 2>/dev/null
free -h; df -h /
```

## Review Focus (кандидаты)

1. Подмена и повтор команд (сервер или посредник): подпись, номер, срок, привязка ключа через код.
2. Сеть не мешает учёту: обрыв, медленный сервер, большой ответ, неверный JSON — служба живёт, блокировки работают (PL-46 «сбой датчика»).
3. NFR-1: выключено — 0 соединений; включено — только адрес из настроек; страж, значок, окна без сети.
4. Те же правила доп. времени, что и с компьютера (предел, журнал, «Отменить»), без второго пути учёта (PL класса A — одна истина).
5. VPS: не трогать n8n, порт только на 127.0.0.1, обновление контейнера без простоя n8n.
